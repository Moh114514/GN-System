# 客户生命周期与施术结束提醒

## 当前规则

客户生命周期固定为三个机器键：

- `booked`：已预约
- `arrived`：已到院
- `treatment_completed`：施术结束

只允许按 `booked -> arrived -> treatment_completed` 前进；超级管理员仍可按既有权限回退。新建客户默认进入 `booked`。

新建客户时可从有效的内部用户中显式选择负责人，默认当前登录用户；该负责人同时写入客户归属和首次到院预约。执行操作的用户仅作为操作人与审计主体，不会覆盖业务负责人。

客户管理列表支持按当前访问范围内的客服负责人筛选，并将 `ownerId` 保留在 URL；客服进入列表时，自己的客户在 SQL 排序中优先于同范围的其他客户，再按建档时间倒序。BD 和超级管理员保持原有范围内的列表顺序，手工传入跨业务组负责人 ID 也不会绕过客户访问范围。

配置中心只允许修改阶段和状态的显示名称；阶段数量、状态机器键、排序、启用状态、所属阶段和两条前进关系均由系统固定。客户详情使用三步只读 Stepper 展示当前节点和下一步。

## 一次性清理迁移

`2026_08_18_000100_simplify_customer_lifecycle` 是部署时执行一次的破坏性数据清理迁移。它清空旧客户状态、状态流转、状态历史，以及旧术后系统提醒、旧生命周期系统规则和旧系统模板关联提醒，然后重新建立三个状态和两条前进关系；预约类型的系统提醒不会因为 `source_type=system` 被整体删除。

迁移不会删除 `customers`、订单或代理商。`down()` 只撤销新增的 `treatment_completed_at` 字段，不承诺恢复已清理的历史数据，因此正式环境执行前必须完成数据库备份和验收确认。

## 施术结束提醒

`CustomerStatusManager` 在状态变为 `treatment_completed` 时通过 Reminder Application Contract 调度两条被动提醒：术后 7 天和术后 30 天。每条提醒的幂等键由客户、施术结束时间和提醒类型组成；回退后再次设置相同结束时间不会重复创建。

直客方案 PR4 对提醒来源做了显式隔离：预约客户都会收到到店前一天 18:00 和到店当天 09:00 的两条独立提醒；术后 7 天和 30 天提醒仅对 `source_type=direct` 生效，代理商客户即使被 `all_customers` 主动提醒规则覆盖，也不会因 `completed_on` 生成术后类提醒。来源类型通过 Customer/Order 的 Reminder Application Data 传递，不改变 Customer 与 Reminder 的模块边界。

客户的 `treatment_completed_at` 会被保存，作为提醒日期和幂等依据。提醒默认使用客户负责人作为 `assigned_to`；如负责人绑定了钉钉 `user_id` 或 `mobile`，发送钉钉通知时会通过 Webhook 对应的定向字段尝试 @，不会在正文暴露该内部绑定值。

## 验证

相关验收覆盖：三状态与前进/回退、施术结束提醒数量和幂等、历史生命周期清理、中文/韩文显示、客户日期筛选、负责人筛选与客服本人优先排序，以及提醒发送链路。

## PR1–PR6 负责人和权限协作

Customer 继续拥有客户负责人、负责人历史、状态流转和跟进记录；负责人移交只改变未来预约、
未完成提醒和当前客户负责人，不改写历史跟进创建人。Auth 提供角色与有效业务组范围，Customer
在 Application 层按 `AccessContext` 过滤客户并在移交、状态回退和敏感字段下载时重新检查权限。

直客方案 PR2 增加 `direct` 来源客户的独立建档、编辑和列表入口。Customer 通过 Auth 的内部用户引用契约取得有效直客负责人，不把直客负责人加入 BD/客服业务组；直客编号使用 `DC` 序列。直客负责人只能访问本人 owner 的直客，转移申请由超级管理员审批，转移仍更新未来预约、未完成提醒和负责人历史，不改写历史跟进创建人。

代理商客户管理列表与其顶部概览固定限定 `source_type=agent`，列表及表单只向超级管理员、BD 和客服开放；直客列表及表单只向超级管理员和直客负责人开放。直客详情使用 `direct-customers.show`，仍复用 `CustomerDetail`；原 `customers.show` 打开直客时先检查来源与访问范围，再重定向到直客详情。编辑页返回对应来源的详情，详情返回对应来源的列表。

客服的代理商客户列表筛选项只包含本人负责的代理商客户实际关联且仍在有效访问范围内的活动代理商；新建客户表单仍可选择有效业务范围内的活动代理商。直客列表、详情和表单的字典选项只返回机构、直客渠道、状态和阶段；直客负责人不接收其他负责人的候选项，超级管理员才可取得直客负责人候选项。直客状态筛选对两类可访问角色显示，负责人筛选只向超级管理员显示。

直客方案 PR3 由 Order 负责完成订单来源判定：直客订单不接受前端传入代理商，使用客户当前的直客渠道和负责人生成订单快照；代理商订单仍沿用代理商业务归属和推广费。Settlement 新增按生效日期版本化的直客提成规则与订单提成快照，金额按 `order_amount_krw * rate_bps / 10000` 向下取整；负责人转移不改写历史提成，新订单使用转移后的负责人。订单完成回退会作废直客提成并保留审计记录，重新完成生成新的有效快照。管理员配置入口和直客负责人个人提成入口均受现有认证与范围规则保护。

直客渠道由 Customer 拥有，在现有直客业务配置页内嵌局部组件维护。只有超级管理员可读取管理列表或新增、编辑、排序、启停，Application 服务在每次操作时重新授权并记录前后值、操作者和本地化审计消息。渠道代码最多 32 位、小写字母开头且仅含小写字母/数字/下划线，保存后不可修改；名称最多 255 字，排序范围按已有 PostgreSQL smallint 为 0–32767。停用只排除新增选择，既有客户可保留原渠道继续编辑，不可换到其他停用渠道；客户引用与历史订单快照不被改写，无删除入口。此能力不新增 migration 或跨模块契约。

机构回传形成正式订单及其订单事实由 Order 负责，Customer 通过治疗完成 Application Contract
完成客户状态变更，不直接创建订单或提醒。负责人、业务组和订单归属的 UAT 映射及抽样步骤见
[PR7 UAT 迁移与发布收尾手册](../operations/pr7-uat-migration-runbook.md)。
