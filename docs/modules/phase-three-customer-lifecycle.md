# Phase 3 客户全生命周期

## 当前能力

所有已认证内部用户可以访问客户列表、建档、编辑和详情页。列表按建档时间倒序，
支持姓名/编号模糊搜索、完整联系方式盲索引精确搜索，以及状态、来源代理商、机构
筛选和 20/50/100 分页。列表中的联系方式与证件号始终脱敏，详情页按当前两档权限
口径向内部用户展示完整值。

建档要求姓名、出生日期、联系方式、意向项目、证件号、来源、机构和到店日期。
Customer 保存档案，Order 通过同步 Application Contract 保存首次预约，Audit
保存操作日志；三者处于同一 PostgreSQL 事务。

## 编号与重复候选

- 代理商客户使用 `{代理商编号}-四位流水`。
- 客户必须归属代理商，使用 `{代理商编号}-四位流水`。
- 自动编号预览必须人工确认；提交时锁定对应编号序列。若并发建档使预览失效，系统
  明确要求刷新和重新确认，不静默改号。
- 手工编号必须符合所选来源前缀，且会推进对应序列以避免后续自动生成冲突。
- 联系方式和证件号通过 HMAC 盲索引匹配。疑似重复只提示候选，不自动合并。
- 客户编号创建后不可编辑。

## 生命周期与时间轴

现有五阶段、七状态使用稳定机器键；新客户默认进入 `interested`。显示名称、排序、
启用状态和允许的前进关系由超级管理员配置，`interested` 不可停用。
基线阶段、状态和顺序转移由幂等 migration 初始化，部署不依赖手工执行 Seeder；
已存在的显示名称、排序和启用状态不会被初始化过程覆盖。配置列表按排序数字从小到大
展示，数字相同时按稳定机器键排序。页面字段悬停说明配置影响，初始化缺失时显示明确
错误提示而不是空白卡片。

普通内部用户只能沿启用的状态转移前进；超级管理员可带原因回退。每次变化写入
`customer_status_histories` 和 activity log。客户详情聚合建档、预约、订单、跟进、
状态和档案修改事件，可按事件类型筛选。

历史导入允许新客户暂时没有当前状态；对已有客户未提供状态时不会覆盖原状态，提供
未知状态名称则在导入提交前明确失败。无当前状态的客户可以通过一次带原因的状态变更
完成首次设定，并以 `from_status_id = NULL` 记录状态历史。

## 模块契约与数据所有权

- Customer 拥有客户、联系方式、证件、编号序列、状态、转移规则和状态历史。
- Agent 与 Config 提供客户归属代理商和机构引用查询。
- Order 提供首次预约写入、机构筛选以及预约/订单时间轴查询。
- Reminder 提供跟进写入与时间轴查询。
- Audit 提供带主体、事件、操作者、IP 和差异属性的审计写入与读取。

跨模块规则见 [ADR-0005](../adr/0005-daily-application-contracts.md)。

## 当前限制

- 本阶段只读展示订单和已有预约，不提供完整订单 CRUD。
- 跟进只登记历史记录；自动提醒、钉钉推送和提醒调度属于后续阶段。
- 联系方式搜索仅支持规范化后的完整值精确匹配，不对加密字段做模糊搜索。
