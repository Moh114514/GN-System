# ADR-0009：月结批次成员关系与历史月结来源

## 状态

Accepted

## 背景

`SettlementRun` is an execution batch, while `Settlement` is the monthly
settlement business fact. Existing settlement records can be discovered by a
later run without being generated by that run. Run-level JSON counters cannot
represent that relationship reliably or render every processed agent.

## Decision

1. `settlement_run_id` on `settlements` identifies the run that generated the
   settlement. It is not a generic “run touched this settlement” field.
2. `import_batch_id` identifies the historical import source.
3. `settlement_run_members` is the authoritative per-agent result for a run.
   Its outcomes are `pending`, `generated`, `existing`, and `failed`.
4. `generated` and `existing` members must reference a settlement. Failed
   members persist a structured message key and parameters.
5. Discovering an imported settlement as `existing` never changes its
   `settlement_run_id` or historical source.
6. Run counters, status, totals, legacy `existing_agent_ids`, and legacy
   `errors` are compatibility projections rebuilt from members during the
   compatibility period.
7. Historical settlement items are materialized only from existing
   `OrderCommission` snapshots after their totals match exactly. Historical
   commission configuration is never re-evaluated.

## Consequences

The center can render generated, existing, and failed members uniformly, retry
one failed member, and distinguish cycle totals from newly generated totals.
Historical imports retain an agent identity snapshot and rollback is blocked
with a business message once a settlement is referenced by a run member.

The compatibility JSON columns remain until at least one stable deployment has
completed UAT and production verification; they are not the source of truth.
