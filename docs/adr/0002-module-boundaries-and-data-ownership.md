# ADR-0002：模块边界与数据所有权

- 状态：Accepted
- 日期：2026-07-27

## 背景

GN-System 采用模块化单体。业务源文档提出模块可通过 Application Contract、
Application Service 或领域事件协作，但 Phase 1 尚未实现这些机制。当前
`ModuleBoundaryTest` 实际禁止任意业务模块命名空间之间的导入。

如果在公共契约位置、事务边界和数据所有权尚未确定时放开跨模块引用，模块骨架
容易演变成相互依赖的单体。

## 决策

- 每个业务模块拥有并且只能写入自己的领域数据。
- 其他模块不得直接引用该模块的 Model、具体 Service 或 Repository，也不得直接
  写入其数据表。
- Phase 1 维持“业务模块之间零命名空间导入”的严格自动化规则。
- Application Contract、Application Service 和领域事件只作为演进方向。首次
  出现真实跨模块用例时，必须另行确认契约位置、依赖方向、同步/异步语义与事务
  边界，然后同步更新本文决策的后继 ADR 和边界测试。
- `app/Infrastructure` 只承载共享技术能力，不作为绕过业务模块所有权的通道。

## 理由

- 当前业务模块尚无数据模型，严格隔离成本最低，也能避免提前设计错误抽象。
- 数据单一写入所有者可以减少循环依赖和跨域事务。
- 让自动化测试描述当前真正允许的依赖，比记录尚未实现的理想结构更可靠。

## 后果

- 当前不能直接从一个业务模块导入另一个模块的 Contract 或 Event。
- 第一项跨模块业务功能需要先完成契约机制设计，不能只修改调用代码。
- 动态类名、原生 SQL 和表所有权不能由现有测试完全检查，仍需代码审查和集成测试。
- 各模块的数据所有权将在相应模块首次实现时写入模块文档。

## 验证

- `tests/Unit/ModuleBoundaryTest.php` 持续检查跨模块 PHP 导入。
- 涉及业务表的变更通过 migration、模块文档和测试说明数据所有者。
- Pull Request 模板要求作者声明模块边界影响。
