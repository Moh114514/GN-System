# ADR-0003：单机局域网生产部署基线

- 状态：Accepted
- 日期：2026-07-27

## 背景

GN-System 需要部署到另一台电脑，供 10～50 名内部用户在局域网使用。系统强调
事务一致性，但并不要求双机高可用或零停机发布。开发 Compose 包含源码挂载、
Vite 和开发入口，不能直接承担长期生产运行。

## 决策

生产环境采用 Ubuntu Server 24.04 LTS 上的单机 Docker Compose，保持 Laravel
模块化单体、单 PostgreSQL 和单 Redis。生产运行使用独立
`compose.production.yaml` 和不可变版本镜像，不继承开发 Compose。

Nginx 在容器内终止 HTTPS，只向指定局域网地址发布 80/443；PostgreSQL、Redis
和 PHP-FPM 不发布宿主端口。证书和私钥只读挂载。数据库、Redis、私有文件及备份
脱离容器可写层持久化，备份每小时同步到异机挂载点。

发布允许 5～10 分钟维护窗口。Migration 必须遵循 expand/contract：先增加兼容
结构并发布兼容代码，旧字段或表只能在后续独立版本删除。健康检查失败且没有不兼容
迁移时回退镜像；存在不兼容数据变更时从部署前备份恢复。

首版使用小时级加密 SQL Dump，数据库 RPO 目标不超过一小时；暂不引入 Kubernetes、
微服务、主从复制、Redis Sentinel 或 WAL/PITR。

## 理由

单机拓扑与当前团队规模、并发量和维护能力匹配，能保留数据库事务的一致性优势。
独立生产 Compose 避免开发工具、源码挂载和自动迁移进入服务器。小时级 Dump 和
异机副本能以较低运维复杂度覆盖当前恢复目标。

## 后果

- 服务器、证书、内网 DNS、UPS 和异机存储仍需按部署文档准备。
- 计划内发布会短暂中断服务，单机故障期间系统不可用。
- 后续 migration 和发布代码必须保持前后版本兼容。
- 当一小时数据损失不可接受或 Dump 明显影响业务时，必须用后继 ADR 评估 PITR。
- 密钥和备份密码必须在密码管理器或离线恢复信封中保留第二份。

## 验证

- 生产镜像阶段和 `compose.production.yaml` 不包含 Vite、源码挂载或内部服务端口。
- CI 构建 app/web 镜像并检查开发文件和开发依赖不存在。
- `/up`、`/health` 和 `/health/operations` 分别覆盖进程、依赖和运维心跳。
- 发布、异机同步、恢复脚本及月度恢复演练按生产部署手册执行。
