## 1. 架构设计目标与约束

### 1.1 设计目标

| 维度 | 目标 | 来源 |
|------|------|------|
| 正确性 | 金额计算**精确到分**，根治 Excel `#VALUE!` 浮点误差 | FR-03-03 / C3 |
| 性能 | 月结 1000 条 < 5 分钟；看板 < 2 秒；页面加载 < 1.5 秒 | NFR-P01/P02 |
| 可扩展 | 规则引擎、代理商等级、提醒场景均可配置扩展，无需改代码 | C3-2 / F2 |
| 可维护 | 职责清晰、模块低耦合，单人/小团队可长期维护 | 团队现实 |
| 合规安全 | 敏感信息脱敏、操作留痕、权限两档 | FR-02-07 / NFR-S |

### 1.2 关键约束（决定架构走向）

- **团队规模**：小团队（1–3 名开发），无专职运维/SRE
- **用户规模**：内部使用，并发低（预估 < 100 同时在線），数据量中等（首期 10 万级，远期百万级）
- **数据强一致**：推广费核算依赖 客户 / 订单 / 代理商 三方可变数据，需事务一致性
- **交付节奏**：需求已稳定，希望尽快落地 MVP，不追求技术炫技

## 2. 整体架构模式

### 2.1 决策：模块化单体（Modular Monolith）

> **采用模块化单体，而非微服务。**

系统由**一个可部署单元（单一 Laravel 应用）**构成，但内部按**领域模块**严格切分边界，模块间通过应用服务 / 领域事件通信，禁止跨模块直接访问对方数据模型。

### 2.2 为什么不是微服务

| 微服务的前提 | 本项目现状 | 结论 |
|--------------|--------------|------|
| 多团队独立开发与部署 | 小团队单代码库 | 不需要 |
| 某些模块需独立扩缩容 | 全员内部使用，负载均匀且低 | 不需要 |
| 技术异构（不同模块用不同语言） | 统一 PHP/Laravel | 不需要 |
| 故障隔离要求极高 | 内部工具，可接受整体停机维护 | 过度设计 |

微服务的代价（服务网格、分布式事务、链路追踪、独立流水线）在本项目纯属负担，且会**直接破坏推广费核算所需的事务一致性**（跨服务分布式事务极难做对）。

### 2.3 为什么是"模块化"而非"大泥球"

单体最大的风险是随着迭代变成耦合泥球。模块化单体用**边界纪律**换取微服务的可维护性，却保留单体的简单性：

- 模块 = 一个领域目录（`app/Modules/{Domain}/`）
- 每个模块内含：`Models / Services / Repositories / Livewire / Events / Routes`
- 跨模块调用**只走对方暴露的 Service 接口或领域事件**，不直接 `new` 对方 Model
- 未来若真需独立（如"报表"模块压力陡增），可整模块抽离为独立服务——**这是微服务的廉价退路**

### 2.4 分层结构

```
┌──────────────────────────────────────────────────────────┐
│                      表现层 (Presentation)                  │
│   Livewire 全页组件 + Alpine.js 微交互 + FluxUI 组件      │
│   Three.js（仅首页 Hero 等点缀性沉浸效果，可选）          │
└──────────────────────────────────────────────────────────┘
                          │ (HTTP / Livewire AJAX)
┌──────────────────────────────────────────────────────────┐
│                     应用层 (Application)                    │
│   用例编排：Form Requests 校验 / Action / Command          │
│   领域事件派发 (OrderCompleted → 触发核算/提醒)           │
└──────────────────────────────────────────────────────────┘
                          │
┌──────────────────────────────────────────────────────────┐
│                      领域层 (Domain)                       │
│   各模块 Models / 业务规则 / 规则引擎(浅) / 状态机       │
│   金额计算统一走 brick/math BigDecimal                    │
└──────────────────────────────────────────────────────────┘
                          │
┌──────────────────────────────────────────────────────────┐
│                   基础设施层 (Infrastructure)                 │
│   PostgreSQL / Redis(缓存+队列) / DingTalk / 文件存储     │
│   Excel 导入 / Word·PDF 生成 / 审计日志 / Sentry         │
└──────────────────────────────────────────────────────────┘
```

依赖方向严格自上而下（表现 → 应用 → 领域 → 基础设施），**禁止反向依赖**，保证领域逻辑可独立测试。

## 3. 核心模块划分与职责

系统划分为 **9 个领域模块 + 1 个基础设施层**：

| # | 模块 | 核心职责 | 依赖（读 / 写） |
|---|------|----------|----------|
| M1 | **Auth 认证与权限** | 登录、2FA、两档角色（超级管理员 / 普通内部用户）、菜单与按钮级可见性 | 横切全部 |
| M2 | **Customer 客户域** | 客户建档、档案、5 阶段/7 档状态机、Excel 批量导入与回滚、详情聚合 | 读 Agent；写自身 |
| M3 | **Agent 代理商域** | 代理商档案、政策体系、等级、合作状态（合作中/暂停/已终止）、升降级建议 | 读 Customer/Order（统计）；写自身 |
| M4 | **Order 订单域** | 订单录入、人工填写成交金额（高精度）、状态变更 | 读 Customer/Agent；写自身 |
| M5 | **Settlement 结算域** | 佣金规则引擎（浅）、月结（周期可由用户自定义触发时间与结算范围，**默认自然月**）、结算单 Word/PDF、财务审核 | 读 Order/Agent/Config；写 settlement |
| M6 | **Reminder 提醒域** | 提醒规则引擎（浅）、模板库、钉钉推送、提醒执行日志、客服自定义 | 读 Customer/Order；写 reminders |
| M7 | **Report 报表域** | to B / to C 双视角看板、ECharts 图表、预聚合表、导出 PDF/图片/HTML | 只读各域 + 预聚合表 |
| M8 | **Config 配置中心** | 政策体系、等级、佣金规则、状态阶段定义、用户管理 | 写配置；被各域读 |
| M9 | **Audit 审计日志** | 全量操作留痕（谁/何时/为何变更） | 横切只写 |
| — | **Infra 基础设施** | Excel 导入、队列、缓存、文件、监控、备份 | 服务全部模块 |

> **模块边界纪律**：M5 算推广费时，**不直接查 Order 表拼 SQL**，而是调用 `OrderModule::getMonthlySettlementData(agentId, month)` 拿到聚合结果，再套用 `ConfigModule` 提供的规则快照。这样 Agent 的等级调整、规则变更都不会让 M5 失控。
>
> **依赖方向说明**：上表"读/写"标注明确——模块间只允许**读依赖**（查对方聚合数据），**写操作必须归属数据所属模块**。例如 M3 Agent 统计客户数时只读 Customer，不允许反向写 Customer。从源头上避免循环写依赖。

## 4. 模块间通信与数据流向

### 4.1 通信方式总览

| 通信场景 | 方式 | 理由 |
|----------|------|------|
| 同请求内的模块协作 | **应用服务直接调用**（同步，进程内） | 简单、强一致，如建档时同步生成客户编号 |
| 跨模块副作用 | **Laravel 领域事件**（解耦） | 订单完成 → 派发 `OrderCompleted`，由监听者异步核算/排提醒 |
| 耗时操作 | **队列（Redis + Queue）** | 月结、Excel 导入、钉钉推送、报表预聚合异步化 |
| 前端 ↔ 后端 | **Livewire AJAX**（wire:model / wire:click） | 无独立 API/SPA，单一代码库，开发最快 |
| 外部系统 | **DingTalk Webhook** | 推送提醒（Q13 确认） |

### 4.2 核心数据流

**① 客户建档 → 状态流转（同步主链路）**
```
客服提交表单 → Auth(鉴权) → CustomerService.create()  [DB 事务]
   ├─ 生成客户编号(代理商编号-4位流水，DB 唯一约束 + 重试兜底)
   ├─ 状态机置"新线索"
   └─ 写入 Audit 日志
→ 返回 Livewire 响应，页面局部刷新
```

**② 订单完成 → 推广费核算 + 提醒排程（事件异步）**
```
OrderService.complete(order)  [DB 事务：订单状态 + 派发事件]
   └─ 派发 OrderCompleted 事件
        ├─► Listener A（同步）：CommissionService.calculate()
        │      读取 Agent 规则快照 → brick/math 算推广费 → 写 settlement_item [同一事务]
        └─► Listener B（队列）：ReminderScheduler.onOrder()
               一次性生成术后系列提醒实例(1/7/30/90/180天) 入库
               到点由 Cron 扫描 → 钉钉推送
```
> **事务边界**：订单状态变更与推广费写入在**同一 DB 事务**内（Listener A 同步），保证"订单完成即核算完成"的一致性；提醒排程（Listener B）走队列异步，不阻塞主事务。

**③ 月结（定时批量，周期可配置）**
```
按用户设定周期触发（默认自然月：每月1日 09:00）  Cron → SettlementCommand::run(month)
   └─ 队列拆批（每代理商一个 Job）
        ├─ 汇总该代理商上月订单金额
        ├─ 读"月度累计阶梯"规则快照 → 算推广费
        ├─ 生成 settlement 主单 + settlement_items 明细
        └─ 完成 → 派发 SettlementGenerated
                 └─► 财务钉钉通知 + 写 Audit
财务审核（Livewire 页面）→ 一键导出 Word/PDF
```

**④ 看板数据（读模型 / 轻量 CQRS）**
```
ReportController → 读 预聚合表(daily_agent_metric / monthly_report)
   └─ ECharts 渲染（to B / to C 两视角）
   └─ 导出 PDF / 图片 / HTML（队列生成文件）
```
> 看板**不直查业务主表**，只读预聚合结果，保证 < 2 秒。写操作落主表，读操作走预聚合表——这是**轻量 CQRS**（读写分离），由定时任务把主表数据物化进预聚合表。

### 4.3 架构图（简版）

> 完整架构图见对话内渲染的 SVG 分层结构图。下方为快速浏览用简版：

```
浏览器(Livewire+Alpine+FluxUI) → Nginx → Laravel 模块化单体(9模块)
                                          │ 领域事件
                                   异步队列 Worker → 钉钉
                                          │

                        Cron(调度) · Sentry(监控) · 自动备份
```

## 5. 数据存储方案

### 5.1 主数据库：PostgreSQL（推荐）/ MySQL

统一关系型数据库，单库多表。**推荐 PostgreSQL**：对 JSONB（规则快照灵活存储）、复合索引、并发事务支持更优；若团队更熟 MySQL 亦可，下文以 PostgreSQL 为例。

### 5.2 🔴 金额精度方案（根治 `#VALUE!` 的核心）

| 项目 | 方案 |
|------|------|
| **存储** | 所有金额列用 `BIGINT`（单位：**分**），如 `amount_cents`。杜绝 `FLOAT`/`DOUBLE` |
| **计算** | PHP 侧使用 `brick/math` 的 `BigDecimal` 做乘除与阶梯匹配，结果舍入到分 |
| **展示** | 读取时 `amount_cents / 100` 格式化，前端仅展示不计算 |
| **快照** | 每笔结算明细固化当时使用的 `比例 / 阶梯区间 / 规则版本`，历史不受后续调整影响（Q20 确认） |

> **为什么不用 `DECIMAL` 类型？** `DECIMAL(20,4)` 也能存精确值，但 PHP 侧仍易在运算/序列化时退化成浮点；用**整数分**从存储到计算全程无浮点，且聚合（SUM）性能更好、索引更友好，是金额存储的行业最佳实践。Excel 的 `#VALUE!` 本质是浮点，系统端用**整数分 + 高精度库**彻底隔离。

### 5.3 核心表（逻辑模型，非 DDL 全量）

| 表 | 关键作用 | 备注 |
|----|----------|------|
| `customers` | 客户主档 | 客户编号(唯一约束)、护照号(加密存储)、状态机字段 |
| `agents` | 代理商主档 | 代理商编号(唯一，全大写+横杠)；类型代码三种 JG=机构/GT=个体户/KR=在韩代理；JG/GT 类用 `简称-类型代码`、KR 类用 `类型代码-简称`；合作状态字段 |
| `policy_systems` | 政策体系（两层结构上层） | 可自由增删 |
| `policy_grades` | 等级（下层，每体系下多个） | 绑定一套默认佣金规则 |
| `commission_rules` | 佣金规则（浅引擎：比例 + 月度累计阶梯区间） | JSONB 存阶梯区间 |
| `agent_rule_overrides` | 单代理商个性化覆盖 | 覆盖等级默认 |
| `orders` | 订单（人工成交金额） | amount_cents、agent_id、customer_id |
| `settlements` / `settlement_items` | 月结主单 / 明细 | 明细含规则快照 |
| `reminder_rules` / `reminder_templates` / `reminders` | 提醒规则 / 模板 / 实例 | 规则引擎(浅) |
| `users` | 用户（两档角色） | is_super_admin 布尔即可 |
| `daily_agent_metric` / `monthly_report` | 预聚合报表表 | 看板只读，定时刷新 |
| `audit_logs` | 审计留痕 | 横切全模块 |
| `config_snapshots` | 配置版本快照（JSONB） | 按 config_type 分类（佣金规则/状态流转/月结周期），支持差异对比与回滚，回滚不影响历史推广费（FR-07-08） |
| `agent_type_codes` | 代理商类型代码 | JG/GT/KR 系统默认保护（只停不删），管理员可新增自定义代码（如 VIP/OS），2-4 位大写字母数字全局唯一（FR-07-09） |

### 5.4 索引与查询（9 维多维查询）

- 多维查询固定 9 个维度、仅 AND 关系（Q08 确认）→ 在常用组合列上建**复合索引**（如 `(agent_id, project, settled_at)`）
- 数据量 < 100 万时，PostgreSQL 复合索引 + 合理分页即可满足；
- **升级路径**：若远期超百万且查询变慢，引入 **Meilisearch** 做只读搜索索引（已在技术路线文档预留），应用层 Repository 接口不变，仅替换实现。

### 5.5 缓存、队列与文件

| 用途 | 技术 | 说明 |
|------|------|------|
| 配置缓存 | Redis | 政策/等级/规则热加载，改完即刷 |
| 看板查询缓存 | Redis | 预聚合结果缓存，TTL 5 分钟 |
| 月结进度 | Redis | 实时进度条（Q：<5分钟/1000条） |
| 异步队列 | Redis Queue + (可选) Horizon | 月结/导入/推送/预聚合 |
| 结算单 Word/PDF | 本地磁盘 / 对象存储 | 生成后供下载 |
| Excel 导入 | 临时存储 + 预演环境 | 导入前 100 条试运行（路线文档策略） |

> **Redis 降级策略**：Redis 不可用时，缓存层自动跳过（直读 DB，性能略降但可用）；队列降级为 `sync` 同步驱动（仅影响异步任务时效，不丢数据）。保证 Redis 单点故障不致系统不可用。

## 6. 关键技术决策及理由

| # | 决策 | 选择 | 理由 | 关联需求 |
|---|------|------|------|----------|
| D1 | 架构形态 | **模块化单体** | 小团队、强一致、低并发，微服务纯增负担；保留抽离退路 | 全局 |
| D2 | 前端形态 | **Livewire + FluxUI，不做独立 SPA** | 单一代码库、开发最快、FluxUI 直接出高级 UI；避免 API+SPA 双倍成本 | 全局 |
| D3 | 金额精度 | **BIGINT 分 + brick/math** | 根治 `#VALUE!` 浮点误差，历史可审计 | FR-03-03/C3 |
| D4 | 规则引擎 | **浅深度：配置化参数（比例+月度累计阶梯）+ DB 规则表** | 平衡灵活与成本，不做 DSL/表达式（F3 确认） | C3-2/F3 |
| D5 | 历史不变性 | **规则快照** | 比例/等级变更立即生效但不影响历史（Q20） | FR-03-03 |
| D6 | 模块解耦 | **领域事件 + 队列** | 订单完成异步触发核算/提醒，请求不被拖慢 | M4→M5/M6 |
| D7 | 看板性能 | **预聚合表 + Redis 缓存（轻量 CQRS）** | 看板 < 2 秒，不直查主表 | NFR-P02/M7 |
| D8 | 推送渠道 | **DingTalk Webhook** | Q13 确认仅钉钉 | FR-04-04/07 |
| D9 | 权限模型 | **两档（超级管理员/普通内部用户）** | C3-4 最简实现，普通用户看全量（Q12 不限制） | NFR-S02 |
| D10 | 报表导出 | **PDF / 图片(PNG) / HTML 三格式** | Q14 确认 | FR-06-02 |
| D11 | 状态流转 | **后台可配置**，当前 5 阶段/7 档命名与流转规则作为**系统默认值** | 2026-07-24 修订（原"开发写死"） | FR-07-04 |
| D12 | 沉浸视觉 | **Three.js 仅用于首页 Hero 等点缀** | 提升"高级感"但不拖累性能与可维护性 | 设计增强 |

## 7. 部署架构

```
                ┌──────────── 单台应用服务器 (Docker) ────────────┐
                │                                               │
  用户 ──►  Nginx  ──►  PHP-FPM (Laravel + Livewire)         │
                │           │                                    │
                │           ├──► Redis (Cache + Queue)            │
                │           ├──► PostgreSQL                       │
                │           └──► Cron (月结/提醒调度触发器)        │
                │                                               │
                │   DingTalk Webhook（出站，不暴露端口）          │
                └───────────────────────────────────────────────┘
                         Sentry(监控) · 自动备份(PostgreSQL)
```

- **容器化**：Docker Compose 一键起（nginx + php-fpm + redis + postgres），本地与生产同构
- **CI/CD**：GitHub Actions 跑 Pest 测试 + PHPStan + Pint，通过后部署
- **调度**：`Cron → artisan schedule:run`，由 Laravel Scheduler 派发月结/提醒
- **可观测**：Sentry 捕获异常；Supervisor 守护队列 Worker
- **备份与灾恢**：
  - PostgreSQL 每日全量 + WAL 归档（可做时间点恢复）；备份文件异地存放
  - 结算单 Word/PDF 与导入文件单独备份
  - RPO ≤ 24 小时、RRT ≤ 4 小时；定期演练恢复流程

## 8. 安全与数据保护

> 本节汇总横切各模块的安全设计，对应需求 Q07（脱敏）、C3-4（权限）、NFR-S。

| 维度 | 方案 |
|------|------|
| **认证** | 账密 + 2FA（超级管理员强制）；登录失败锁定；密码强度策略 |
| **权限（两档）** | 超级管理员（配置中心/等级/规则/月结审核/用户管理）；普通内部用户（建档/跟进/查询/看板，看全量，Q12 不限制）。按钮与菜单级可见性由中间件统一控制 |
| **敏感字段加密** | 护照号、联系方式等使用 Laravel Encryptable 字段级加密存储；列表默认脱敏（如手机号 `138****5678`），详情页按权限解密展示（Q07） |
| **审计留痕** | 所有写操作经 M9 Audit 横切记录：操作人、时间、前后值、来源 IP；审计日志独立表、只追加、不可篡改 |
| **传输安全** | 全站 HTTPS；钉钉 Webhook 出站校验签名 |
| **防注入/XSS** | Eloquent 参数绑定 + Livewire 服务端校验；FluxUI 默认转义输出 |
| **导入安全** | Excel 上传限类型/大小；预演环境试运行，隔离脏数据 |

## 9. 可扩展性 / 可维护性 / 性能

### 9.1 可扩展性（Extensibility）
- **规则可配**：政策体系、等级、佣金阶梯、提醒场景全部配置化，新增代理商类型/提醒节点**零代码**
- **模块可抽离**：模块化边界使任一重模块（如 Report）未来可独立为服务
- **搜索可升级**：多维查询 Repository 接口隔离，底层可无缝换 Meilisearch
- **渠道可加**：提醒推送走 Adapter，未来加企业微信只需新增一个 PushAdapter

### 9.2 可维护性（Maintainability）
- **单一代码库 + 明确分层**，新人易上手
- **领域事件解耦**，改 M5 不影响 M2
- **审计日志横切**，任何变更可溯源
- **FluxUI 组件复用**，UI 一致性高，改主题一处生效

### 9.3 性能（Performance）
- **月结 < 5 分钟/1000 条**：队列拆批 + 规则快照预读 + 避免 N+1
- **看板 < 2 秒**：预聚合表 + Redis 缓存（轻量 CQRS 读写分离），杜绝主表 Join
- **页面 < 1.5 秒**：Livewire 局部刷新 + 关键 CSS 内联 + 懒加载
- **动画 60fps**：高级 CSS（玻璃拟态、磁吸 hover）由 GPU 合成，Three.js 仅点缀且降级处理

## 10. 风险与演进路线

| 风险 | 触发条件 | 应对 |
|------|----------|------|
| 规则复杂度超预期 | 业务方要求条件分支/表达式 | 规则引擎由"浅"升级至"中"，引入条件模型（已在 D4 预留） |
| 数据量暴涨 | 客户/订单超百万 | 多维查询切 Meilisearch；报表表按时分区 |
| 并发上升 | 多机构同时使用 | Redis 横向；PHP-FPM 水平扩容（单体也可多实例） |
| 需独立部署某模块 | Report 压力陡增 | 按模块边界抽离为微服务（D1 退路） |

> **何时 reconsider 微服务**：仅当（a）团队扩到多组且需独立交付，或（b）出现必须隔离的极高可用模块时，才值得付出分布式代价。
