# GN-System 剩余业务模块改造方案

依据：客户管理系统菜单与功能明细表（4页）｜仓库 `develop` 分支 `6016ec0b`｜2026-10-23

我重新核对了 Word 的全部四页，并对照了 GN-System 当前仓库的页面、服务层、数据库模型和权限实现。

本次将总览页面视为已经完成，不再规划其指标、图表和导出改造。

## 一、剩余需求整体评估

Word 第 1 页要求将系统整理成五个一级菜单，后面三页分别详细说明线上直客、线下渠道、合作机构和配置中心的功能。

副本客户管理系统菜单与功能明细表.docx



目前仓库已有大部分底层业务能力，但菜单组织方式、部分管理报表、客户跟进机制还没有达到 Word 中的目标。

| 需求模块         | 现有仓库情况                  | 主要剩余工作             | 优先级 |

这里的 P0 表示应当优先解决的基础性改造，P1 是核心业务功能，P2 是可以复用已有能力的优化。

整体建议：保留原有 Laravel 模块化架构和业务表，优先做导航、页面组织及查询能力的扩展。 仅在 Word 明确需要、现有数据模型确实无法支持时增加数据库字段或新表。

另外，当前远端 `develop` 为 `6016ec0b`，`main` 仍是 `v0.7.0` 对应提交。你刚完成的看板改动可能还在本地或其他分支，因此以下判断以已读取的仓库代码为基线，不把尚未同步的改动认定为缺失功能。

这是建议首先实施的部分，因为后续业务页面都需要挂在新的菜单结构下。

这里需要注意，Word 明确要求五个一级菜单，但并未要求删除原来的功能。

所以建议：

- 原来的客户管理、订单中心、代理商管理等入口，分别迁入线上或线下菜单。
- 现有提醒中心、机构回传、历史导入、月结管理、日志等功能继续保留，通过相关业务页面或配置中心进入。
- 顶部全局搜索和通知铃铛继续保留，不必占用一级菜单。
- 原有 URL 和命名路由尽量保留，避免影响书签、历史链接和系统通知。

订单管理建议复用同一个订单中心。 两个菜单项只需设置不同的默认业务筛选条件，不建议分别开发两套订单 CRUD。

### 2.3 权限调整是一个独立问题

Word 定义了以下四类使用者：

1. 老板
2. 市场部运营总监
3. 线上负责人
4. BD 经理

当前代码的 `UserRole` 实际定义是：

```
SuperAdmin
BdManager
CustomerService
DirectCustomerManager
```

可以先建立以下映射：

| Word 角色 | 当前系统角色                    | 建议               |
| ------- | ------------------------- | ---------------- |
| 老板      | `super_admin`             | 沿用               |
| 市场部运营总监 | 暂无独立角色                    | 建议新增业务管理角色       |
| 线上负责人   | `direct_customer_manager` | 可优先复用            |
| BD 经理   | `bd_manager`              | 沿用               |
| 现有客服    | `customer_service`        | 保留，用于线下渠道客户的业务归属 |

最需要处理的是市场部运营总监。

Word 要求该角色能够访问五个菜单，还可以进入员工与权限、配置中心等页面。当前这些管理页面大多被 `super-admin` 中间件限制。

我不建议直接让运营总监拥有超级管理员身份。业务管理权限和系统安全管理权限应当分开。

如果该角色确实要独立存在，实施时需要修改：

- `app/Modules/Auth/Domain/UserRole.php`
- `app/Modules/Auth/Application/Data/AccessContext.php`
- `app/Modules/Auth/Application/Services/DatabaseAccessContextResolver.php`
- `app/Modules/Auth/Http/Middleware/` 下相关权限中间件
- `app/Modules/Config/Application/Services/ConfigurationUserCoordinator.php`
- 用户管理表单和角色枚举校验
- `users` 的角色约束 Migration

推荐通过明确的业务能力检查控制报表读取、人员管理、机构管理和提成规则管理。

即使运营总监可以管理普通员工，也应限制其授予超级管理员身份、修改自身高级权限以及操作部署和系统安全配置。

### 3.1 团队概览

需要新增业务页面

Word 要求

展示销售额、订单数、成交客户数和各客服业绩，支持按月份和负责人筛选，能够查看关联订单。

当前实现

仓库已有：

`app/Modules/Report/Application/Services/TeamOverviewService.php`

但该服务主要针对 BD 业务组，目前只允许超级管理员和 BD 经理使用。

线上直客尚无符合 Word 要求的专门团队概览页面。

改造方案

建议新增线上团队概览，保留现有线下团队统计。

页面可以设计为以下结构：

| 页面区域  | 显示内容                |
| ----- | ------------------- |
| 筛选区   | 统计月份、线上负责人          |
| 核心指标  | 月销售额、成交订单数、成交客户数    |
| 负责人业绩 | 员工姓名、订单数量、成交金额、客户数量 |
| 订单明细  | 订单编号、客户、机构、金额、成交日期  |

页面顶部按照现有团队统计模式展示 KPI，下面用表格列出各负责人的业绩。

点击某个负责人，进入对应订单明细，筛选条件需要完整传递。

建议实现

在 Report 模块新增：

- `DirectTeamOverviewService.php`
- `DirectTeamOverview.php`
- `resources/views/livewire/reports/direct-team-overview.blade.php`

销售额和订单数量通过 `ReportOrderReader` 扩展只读契约获取；客户数量通过 `ReportCustomerReader` 获取。

对于管理层查看各负责人业绩，需要支持按 `owner_id` 汇总直客订单。不要由 Report 模块直接操作 Order、Customer 数据表。

统计月份建议与现有团队报表保持一致，优先使用订单业务日期 `occurred_on`。订单实际登记时间与业务日期可能不同，因此口径应在页面说明。

验收

管理层可以查看所有授权范围内的直客负责人；普通线上负责人只能查看本人被授权的数据。每位负责人的订单金额之和应当与同口径的团队金额一致。

### 3.4 客服绩效与提成

现有明细需要扩展为业绩报表

Word 要求

展示客服姓名、统计月份、订单数量、实际订单金额合计、适用提成比例、提成金额和订单明细。支持按客服、月份筛选。

- `DirectCustomerCommissionCenter.php`
- `DatabaseDirectOrderCommissionGateway.php`
- `DirectCustomerConfiguration.php`

其中 `direct_order_commissions` 已保存：

- 订单编号
- 提成归属负责人
- 提成比例
- 订单金额
- 提成金额
- 订单完成时间
- 提成状态与规则快照

报表结构建议如下。

| 客服/负责人 | 月份      | 订单数 | 实际成交额       | 提成金额      | 操作   |
| ------ | ------- | --- | ----------- | --------- | ---- |
| 员工 A   | 2026-10 | 8   | ₩ 5,000,000 | ₩ 150,000 | 查看明细 |
| 员工 B   | 2026-10 | 6   | ₩ 3,000,000 | ₩ 90,000  | 查看明细 |

由于提成比例可能随着生效日期发生变化，不能假设一个员工在整个月只适用一个比例。

建议：

- 汇总页展示实际成交额、订单数和最终提成金额。
- 若本月存在多个费率版本，提成比例显示「多档」或实际适用范围。
- 明细页逐笔显示订单对应的真实提成比例。
- 提成计算继续读取现有提成快照。
- 已经生成的历史提成不因为管理员修改比例而被重新计算。

需要明确： Word 使用“客服”称呼，而现有直客提成按 `direct_customer_manager` 的订单归属负责人记录。两者是否为同一类员工需要在角色设计阶段确定。若确实是同一类，可以直接复用现有数据。

### 4.2 跟进记录和提醒任务需要建立关联

目前：

`CustomerFollowupManager.php`

负责保存客户跟进记录。

`ReminderWorkspace.php`

负责提醒任务的完成、延期、转移和取消。

两个功能已经存在，但现有 `recordFollowup()` 只保存跟进记录，不会自动把对应提醒任务标记为完成。

建议统一为以下操作流程。

待跟进提醒

到达设定时间后，通知当前负责人

打开客户档案

查看历史沟通、客户情况与本次任务

提交跟进记录

填写沟通时间、内容、跟进结果和下一次时间

本次任务完成

可选创建下一次跟进提醒

推荐的后台实现方式：

1. 为跟进记录补充结果字段，以及与提醒任务关联的标识。
2. 扩展现有 `CustomerFollowupGateway`。
3. 提交时在事务内保存跟进记录，并完成对应的提醒任务。
4. 填写下一次跟进时间时，自动建立下一条提醒。
5. 每次完成操作保留审计记录。

为避免重复维护时间字段，客户列表中的“下次跟进时间”建议通过最近一条有效未完成跟进任务计算。

不需要同时在客户表和提醒表存储两份下次跟进时间。

### 4.3 客户列表增加跟进信息

现有 `direct-customer-list.blade.php` 主要展示客户姓名、联系方式、渠道、负责人、状态和创建时间。

| 字段     | 展示方式                   |

| 最近跟进时间 | 最后一次有效跟进记录的时间          |
| 下次跟进时间 | 最近一条有效未完成任务的到期时间       |
| 跟进状态   | 待跟进、今日待跟进、即将到期、已逾期、无待办 |

逾期状态使用红色文字或状态标签。

建议列表顶部增加三个可点击的指标：

今日待跟进

# 6

已逾期

# 2

即将到期

# 4

布局示意，数量不代表真实业务数据。

## 十、总体结论

这份 Word 中，剩余工作大体可以分为三个层次。

首先是系统结构调整。 需要把当前分散的业务入口整理成五个一级菜单，同时处理老板、运营总监、线上负责人和 BD 经理的权限关系。

其次是业务功能补齐。 线上团队概览、客服月度绩效、客户跟进任务闭环、线下代理商客户池与 BD 月度业绩，是需要投入主要开发工作量的部分。

最后是现有页面完善。 订单卡片、机构来源筛选、Excel 明细导出、配置中心分类，可以充分复用现有代码。

我建议优先完成 PR1 菜单与权限、PR2 线上业务报表、PR3 客户跟进闭环。这三部分完成后，系统整体使用方式就会明显接近 Word 描述的目标，其余模块大部分可以通过现有能力扩展实现。

以上为方案编写时的结论。方案随后已按本文件末尾的实施记录开始落地；当前代码和验证状态以实施记录及 `docs/project-status.md` 为准。
